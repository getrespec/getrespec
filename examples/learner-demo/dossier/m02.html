First LLM API integration and streaming

Applied AI Engineer

In 30 seconds

A help box for an online bookstore's order page: a customer asks about their order and the answer streams in word by word, with a Stop button and a status line screen readers announce. The model call and its instructions live on the server, so the browser never sees the API key or the prompt. Worth asking about: the Try again button resends the wrong question, and the candidate wasn't sure how to recover from a dropped connection.

Result: 86/100, passed

Best question to ask: Try again sends the word "retry" instead of the customer's question. Walk me through how you'd fix it.

Key decisions

The model call and the system prompt stay on the server

Why
The API key must never reach the browser, and the support instructions (who the assistant is, keep answers short) shouldn't be something a customer can edit in DevTools.
Alternatives
Call the provider directly from the browser with a restricted key, or send the system prompt from the client with each request.
Tradeoff
Every answer takes one extra hop through the app's server, and the server now handles streaming connections.

Pass chunks through as they arrive

Why
Customers should see the first words in under a second instead of waiting for the whole answer; the proxy log shows a median of 354 ms to the first token.
Alternatives
Wait for the full completion and return JSON, or use server-sent events with a message format.
Tradeoff
Plain text streaming is simple, but it carries no structure: the client can't tell a finished answer from a cut-off one without extra signals.

Stop cancels the upstream request, not only the UI

Why
When the customer presses Stop, the server aborts the call to the model, so no tokens are generated (and paid for) that nobody will read.
Alternatives
Hide the rest of the answer in the browser and let the model finish in the background.
Tradeoff
The partial answer is final; there is no way to resume it.

"Stopped" is a state of its own, not an error

Why
The customer chose to stop, and the partial answer is still useful, so it stays on screen with a calm "Stopped" instead of an error message.
Alternatives
Treat every aborted request as an error, or clear the answer on Stop.
Tradeoff
One more state to handle; the retry path was the one that slipped (Try again sends the string "retry" instead of the customer's question).

Questions to ask

  1. Try again sends the word "retry" instead of the customer's question. Walk me through how you'd fix it.
  2. Why did you keep the system prompt on the server rather than sending it from the client?
  3. What does a customer see if the connection drops halfway through an answer, and what should they see?
  4. How would the client know an answer finished normally rather than being cut off?
  5. Stop aborts the upstream call. What would you log to confirm that tokens really stop being generated?
  6. The answer region has no label. How would a screen reader user find the answer after "Answering…"?
  7. How would you add the order's real status (shipped, delayed) so the model doesn't guess?
  8. What would you change if two questions were sent before the first answer finished?
  9. How would you test this without calling the real model?

Defence answers

Why isn't 'stopped' an error?
Because the customer chose it, and the partial answer is still useful.
What would you do if the connection dropped mid-answer?
Show an error and let them try again; I wasn't sure if I could resume.
